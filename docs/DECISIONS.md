# Architecture Decisions

## ADR-001: Deterministic policy engine vs LLM authorization

* **Decision**: We will use a deterministic policy engine written in Python to evaluate transactions against constraints, rather than using an LLM to decide if a transaction is authorized.
* **Reason**: Security and explainability. An LLM may be easily bypassed (prompt injection via item descriptions) or hallucinate a false approval. Financial authorizations must be 100% predictable and auditable.
* **Alternatives**: Using an LLM to compare the intent string directly with the transaction JSON and return a True/False.
* **Consequences**: We must rigidly define the `Intent Contract` and `Transaction Contract` schemas upfront so they can be compared mathematically.

## ADR-002: Modular monolith vs microservices

* **Decision**: We will build PayGuard as a Modular Monolith using FastAPI.
* **Reason**: Given the strict 10-12 day timeline, managing distributed systems overhead (network boundaries, Kafka, distributed tracing, independent deployments) introduces unacceptable risk.
* **Alternatives**: A microservices architecture separating Intent Management, Evaluation, and Payments.
* **Consequences**: All logical domains run in the same process and share a single PostgreSQL database instance. We maintain strict namespace boundaries within the codebase.

## ADR-003: Intent Contract vs Transaction Contract

* **Decision**: We will strictly separate the representation of the user's constraints (`Intent Contract`) from the AI agent's proposed purchase (`Transaction Contract`).
* **Reason**: To maintain clear trust boundaries. The Intent Contract is trusted (owned by the user). The Transaction Contract is untrusted (generated by the agent). 
* **Alternatives**: Merging the desired state and proposed state into a single object.
* **Consequences**: The Policy Engine's primary job is a mapping/comparison operation between two distinct data structures.

## ADR-004: Payment-provider abstraction

* **Decision**: PayGuard will interact with payment gateways through an abstract `PaymentProvider` interface.
* **Reason**: To decouple the core policy engine from Razorpay-specific (or other gateway) semantics. This ensures PayGuard's logic is cleanly focused on authorization, not payment processing details.
* **Alternatives**: Directly calling the Razorpay SDK from the Decision Engine upon `APPROVE`.
* **Consequences**: We must design the abstraction early, even though the actual Razorpay integration is deferred to Phase 4.

## ADR-005: Deterministic constraint violations instead of fuzzy intent-drift scoring

* **Decision**: We will evaluate transactions on an itemized, constraint-by-constraint basis resulting in distinct violations, replacing the original idea of a single "intent drift percentage".
* **Reason**: An intent drift score (e.g., "75% match") is unactionable and difficult to explain. Itemized violations (e.g., `MAX_AMOUNT_EXCEEDED`, `BANNED_CATEGORY`) map directly to concrete user feedback and clear `APPROVE`/`ASK`/`BLOCK` decisions.
* **Alternatives**: Calculating a mathematical distance between the intent and the transaction.
* **Consequences**: The Policy Engine must be capable of generating a list of `Violation` objects for every transaction, and the Decision Engine must know how to weight them (hard vs soft).
